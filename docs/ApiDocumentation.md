## 2. API Base Configuration & Conventions

### 2.1 Proposed Base URL
```text
http://localhost:5000/api
```
*(In deployment, the base URL is configured via environment variables.)*

### 2.2 Authentication Headers by Caller Type

SmartPPE separates human user sessions from hardware and ML service credentials:

| Caller Type | Required Headers | Description |
|---|---|---|
| **Human Users** (`WORKER`, `SUPERVISOR`, `ADMINISTRATOR`) | `Content-Type: application/json`<br>`Authorization: Bearer <JWT_TOKEN>` | JWT issued by `POST /api/auth/login` |
| **ESP32 IoT Devices** | `Content-Type: application/json`<br>`X-Device-Code: <DEVICE_CODE>`<br>`X-Device-Key: <RAW_DEVICE_API_KEY>` | Validated against `devices.apiKeyHash` in the database |
| **ML Inference Service** | `Content-Type: application/json`<br>`X-ML-Service-Key: <ML_SERVICE_API_KEY>` | Validated against the backend's configured ML service credential |

### 2.3 Canonical Timestamp, Identifier & Enum Conventions

To eliminate cross-document mismatches, the following conventions apply across all endpoints:

- **Timestamp Format:** ISO 8601 UTC strings (`"YYYY-MM-DDTHH:mm:ssZ"`, e.g., `"2026-11-25T10:30:00Z"`).
  - **`occurredAt`:** The timestamp when a physical event (RFID scan, camera frame detection, or sensor reading) occurred at the device or ML service.
  - **`createdAt` / `updatedAt`:** Database record creation and modification timestamps generated by the backend.
  - **`lastHeartbeat`:** Timestamp of the most recent device or camera heartbeat received by the backend.
  - **`verifiedAt` / `resolvedAt`:** Timestamps when an incident was verified/rejected or resolved.
- **Hardware & Entity Codes vs. Database IDs:**
  - External hardware and ML payloads identify sources using human-readable registered codes: `deviceCode` (e.g., `"ESP32_001"`) and `cameraCode` (e.g., `"CAM_001"`).
  - The backend resolves `deviceCode` or `cameraCode` to the internal database primary key (`deviceId`, `cameraId`) and its assigned `zoneId`.
- **Canonical Enums (Uppercase Strings):**
  - **User Roles (`role`):** `"WORKER"` | `"SUPERVISOR"` | `"ADMINISTRATOR"`
  - **User Status (`status`):** `"ACTIVE"` | `"INACTIVE"` | `"SUSPENDED"`
  - **Worker / Zone Status (`status`):** `"ACTIVE"` | `"INACTIVE"`
  - **Device / Camera Status (`status`):** `"ONLINE"` | `"OFFLINE"` | `"MAINTENANCE"`
  - **RFID Scan Status (`scanStatus`):** `"SUCCESS"` | `"UNKNOWN_CARD"` | `"DUPLICATE_IGNORED"` | `"REJECTED"`
  - **PPE Safety Status (`safetyStatus`):** `"SAFE"` | `"UNSAFE"` | `"REVIEW_REQUIRED"`
  - **Sensor Type (`sensorType`):** `"SMOKE"` | `"FLAME"`
  - **Sensor Alert Status (`alertStatus`):** `"NORMAL"` | `"WARNING"` | `"CRITICAL"`
  - **Incident Type (`incidentType`):** `"MISSING_HELMET"` | `"MISSING_SAFETY_VEST"` | `"MULTIPLE_PPE_VIOLATION"` | `"SMOKE_DETECTED"` | `"FLAME_DETECTED"` | `"UNKNOWN_RFID"`
  - **Incident Severity (`severity`):** `"LOW"` | `"MEDIUM"` | `"HIGH"` | `"CRITICAL"`
  - **Incident Status (`status`):** `"OPEN"` | `"UNDER_REVIEW"` | `"VERIFIED"` | `"RESOLVED"` | `"REJECTED"`

### 2.4 Standard API Response Envelope

**Success Envelope:**
```json
{
  "success": true,
  "message": "Operation completed successfully",
  "data": {}
}
```

**Error Envelope:**
```json
{
  "success": false,
  "message": "Validation failed",
  "error": {
    "code": "INVALID_PAYLOAD",
    "details": "overallConfidence must be between 0.0 and 1.0"
  }
}
```

## 3. Authentication APIs (`/api/auth`)

### 3.1 User Login
- **Endpoint:** `POST /api/auth/login`
- **Auth Required:** Public (Rate-limited)
- **Request Body:**
```json
{
  "email": "admin@smartppe.local",
  "password": "ExamplePassword123!"
}
```
- **Example Response (`200 OK`):**
```json
{
  "success": true,
  "message": "Login successful",
  "data": {
    "token": "<JWT_ACCESS_TOKEN>",
    "expiresIn": "8h",
    "user": {
      "userId": "usr_01J9Z001",
      "name": "System Administrator",
      "email": "admin@smartppe.local",
      "role": "ADMINISTRATOR",
      "status": "ACTIVE",
      "workerId": null
    }
  }
}
```

### 3.2 Get Current Authenticated User
- **Endpoint:** `GET /api/auth/me` (also available at alias `GET /api/users/me`)
- **Auth Required:** `Bearer <JWT_TOKEN>` (`WORKER`, `SUPERVISOR`, `ADMINISTRATOR`)
- **Description:** Returns the current authenticated user's profile, role, linked `workerId` and `workerZoneId` (if role is `WORKER`), and assigned `assignedZoneIds` (if role is `SUPERVISOR`).

### 3.3 Register User Account (Admin Restricted / First-Admin Bootstrap)
- **Endpoint:** `POST /api/auth/register`
- **Auth Required:** `Bearer <JWT_TOKEN>` (`ADMINISTRATOR` only; unauthenticated allowed **only** when `0` users exist in the database to bootstrap the initial `ADMINISTRATOR` account).
- **Request Body:**
```json
{
  "name": "Zone A Supervisor",
  "email": "supervisor.a@smartppe.local",
  "password": "SupervisorPassword123!",
  "role": "SUPERVISOR"
}
```

### 3.4 User Logout (Revoke Token)
- **Endpoint:** `POST /api/auth/logout`
- **Auth Required:** `Bearer <JWT_TOKEN>`
- **Description:** Revokes the current Bearer token for the active server session.

### 4.1 Register Worker
- **Endpoint:** `POST /api/workers`
- **Auth Required:** `Bearer <JWT_TOKEN>` (`ADMINISTRATOR` only)
- **Request Body:**
```json
{
  "employeeCode": "EMP-001",
  "name": "Test Worker 1",
  "department": "Assembly",
  "designation": "Assembly Technician",
  "zoneId": "zone_01",
  "rfidUid": "A1B2C3D4",
  "userId": "usr_01J9Z050"
}
```
*(Note: `userId` is optional and links the worker profile to a `WORKER` login account in `users`.)*

### 4.2 Get Workers List
- **Endpoint:** `GET /api/workers`
- **Auth Required:** `Bearer <JWT_TOKEN>` (`SUPERVISOR`, `ADMINISTRATOR`)
- **Authorization Rule:**
  - `ADMINISTRATOR`: Returns all workers across all workplace zones (supports `?zoneId=`, `?status=`).
  - `SUPERVISOR`: Returns **only** workers in the supervisor's assigned workplace zones (read-only).
  - `WORKER`: Returns `403 Forbidden` (Workers must use `GET /api/workers/me`).

### 4.3 Get Logged-In Worker's Own Profile (Worker Self-Service)
- **Endpoint:** `GET /api/workers/me`
- **Auth Required:** `Bearer <JWT_TOKEN>` (`WORKER`)
- **Description:** Returns the logged-in worker's own profile (`workerId`, `employeeCode`, `name`, `department`, `designation`, `rfidUid`, assigned `zone`, `status`, and personal compliance summary).

### 4.4 Get Logged-In Worker's Personal Incidents
- **Endpoint:** `GET /api/workers/me/incidents`
- **Auth Required:** `Bearer <JWT_TOKEN>` (`WORKER`)
- **Description:** Returns safety incidents associated with the logged-in worker's `workerId`.

### 4.5 Get, Update, or Deactivate Worker by ID
- `GET /api/workers/:id` — Accessible to `ADMINISTRATOR` and to `SUPERVISOR` (only if worker belongs to supervisor's assigned zone).
- `PUT /api/workers/:id` — `ADMINISTRATOR` only.
- `DELETE /api/workers/:id` — `ADMINISTRATOR` only (soft-deactivates or deletes test worker and records audit log).

## 5. Canonical Contract #1: RFID Identification APIs (`/api/rfid`)

### 5.1 Scan RFID Card (`POST /api/rfid/scan`)

- **Purpose:** Receives an RFID card UID scanned by an ESP32 + MFRC522 reader, resolves the registered worker and zone, applies duplicate-scan cooldown suppression, logs the scan in `rfidLogs`, and flags unknown cards.
- **Authentication Requirements:** ESP32 Device Authentication (`X-Device-Code` and `X-Device-Key` headers).
- **Required Headers:**
  ```http
  Content-Type: application/json
  X-Device-Code: ESP32_001
  X-Device-Key: <RAW_DEVICE_API_KEY>
  ```
- **Request Body Schema:**

| Field | Type | Required | Description & Validation Rules |
|---|---|---|---|
| `deviceCode` | String | **Required** | Unique registered ESP32 identifier (e.g., `"ESP32_001"`). Must match `X-Device-Code` header and exist in `devices` with `status != "MAINTENANCE"`. |
| `rfidUid` | String | **Required** | Scanned 13.56 MHz RFID UID as uppercase hexadecimal string without spaces (4 to 10 bytes = 8 to 20 hex chars, regex `^[0-9A-F]{8,20}$`). |
| `occurredAt` | String (ISO 8601) | Optional | Device timestamp if NTP-synced (e.g., `"2026-11-25T10:30:00Z"`). If omitted or invalid, backend uses server reception time. |
| `firmwareVersion` | String | Optional | Firmware version string (e.g., `"1.0.0"`). |

- **Example Request:**
```json
{
  "deviceCode": "ESP32_001",
  "rfidUid": "A1B2C3D4",
  "occurredAt": "2026-11-25T10:30:00Z",
  "firmwareVersion": "1.0.0"
}
```

- **Example Response — Recognized Worker (`200 OK`):**
```json
{
  "success": true,
  "message": "Worker identified",
  "data": {
    "logId": "rfid_01J9Z100",
    "recognized": true,
    "scanStatus": "SUCCESS",
    "duplicateIgnored": false,
    "zoneId": "zone_01",
    "worker": {
      "workerId": "wrk_01J9Z010",
      "employeeCode": "EMP-001",
      "name": "Test Worker 1",
      "department": "Assembly",
      "assignedZoneId": "zone_01"
    },
    "occurredAt": "2026-11-25T10:30:00Z"
  }
}
```

- **Example Response — Unknown RFID Card (`200 OK`):**
```json
{
  "success": true,
  "message": "Unknown RFID card recorded",
  "data": {
    "logId": "rfid_01J9Z101",
    "recognized": false,
    "scanStatus": "UNKNOWN_CARD",
    "duplicateIgnored": false,
    "zoneId": "zone_01",
    "worker": null,
    "incidentCreated": true,
    "incidentId": "inc_01J9Z200",
    "occurredAt": "2026-11-25T10:31:00Z"
  }
}
```

- **Validation & Error Responses:**
  - `400 Bad Request`: Missing `deviceCode` or `rfidUid`, or `rfidUid` fails hex format validation.
  - `401 Unauthorized`: Missing or invalid `X-Device-Key`.
  - `403 Forbidden`: Device is unregistered or in `"MAINTENANCE"` / `"INACTIVE"` state.

### 5.2 Get RFID Scan History
- **Endpoint:** `GET /api/rfid/logs`
- **Auth Required:** `Bearer <JWT_TOKEN>` (`SUPERVISOR` for assigned zones; `ADMINISTRATOR` for all zones).

### 6.3 ESP32 Device Heartbeat
- **Endpoint:** `POST /api/devices/heartbeat`
- **Auth Required:** `X-Device-Code` and `X-Device-Key` headers
- **Request Body:**
```json
{
  "deviceCode": "ESP32_001",
  "status": "ONLINE",
  "firmwareVersion": "1.0.0",
  "uptimeSeconds": 3600
}
```
- **Behavior:** Updates `lastHeartbeat` to current UTC timestamp and sets `status: "ONLINE"`. If a device sends no heartbeat or event for $> 90$ seconds (configurable), the backend marks it `"OFFLINE"`.

## 8. Canonical Contract #2: PPE Detection APIs (`/api/detections`)

### 8.1 Submit Camera PPE Detection (`POST /api/detections`)

- **Purpose:** Receives structured PPE detection results from the camera-based ML inference pipeline, resolves the camera's assigned `zoneId`, stores the detection record in `ppeDetections`, and creates or updates a PPE violation incident (subject to the deduplication cooldown window) when `safetyStatus` is `"UNSAFE"`.
- **Authentication Requirements:** ML Service Authentication (`X-ML-Service-Key` header).
- **Required Headers:**
  ```http
  Content-Type: application/json
  X-ML-Service-Key: <ML_SERVICE_API_KEY>
  ```
- **Request Body Schema:**

| Field | Type | Required | Description & Validation Rules |
|---|---|---|---|
| `cameraCode` | String | **Required** | Registered camera identifier (e.g., `"CAM_001"`). Must exist in `cameras` table; backend resolves `cameraId` and `zoneId` from this record. |
| `occurredAt` | String (ISO 8601) | **Required** | UTC timestamp when the frame was captured (e.g., `"2026-11-25T10:30:00Z"`). |
| `modelVersion` | String | **Required** | Identifier/version of the ML model (e.g., `"ppe-detector-v1"`). |
| `idempotencyKey` | String | Optional | Unique frame/event key (e.g., `"CAM_001-1764066600000"`) to prevent duplicate ingestion on network retry. |
| `workerId` | String or Null | Optional | Defaults to `null`. Must only be populated if a verified worker-identification mechanism is active. |
| `detections` | Array of Objects | **Required** | Array of detected objects in the frame. Each item requires:<br>- `classLabel` (String, e.g., `"person"`, `"helmet"`, `"no_helmet"`, `"safety_vest"`, `"no_safety_vest"` — exact model labels `TO BE CONFIRMED`)<br>- `confidence` (Number, float `0.0` to `1.0`)<br>- `bbox` (Optional Array of 4 Numbers `[xMin, yMin, xMax, yMax]`) |
| `missingPPE` | Array of Strings | **Required** | List of missing required PPE items (e.g., `[]`, `["helmet"]`, `["safety_vest"]`, or `["helmet", "safety_vest"]`). |
| `safetyStatus` | String | **Required** | Canonical enum: `"SAFE"` \| `"UNSAFE"` \| `"REVIEW_REQUIRED"`. |
| `overallConfidence` | Number | **Required** | Aggregate or minimum triggering confidence score (`0.0 <= overallConfidence <= 1.0`). |
| `evidenceUrl` | String or Null | Optional | Private storage path/reference to the annotated violation snapshot image, if captured. |
| `evidenceFileHash` | String or Null | Optional | Optional SHA-256 hex digest of the snapshot image file for tamper-evident verification. |

- **Example Request:**
```json
{
  "cameraCode": "CAM_001",
  "occurredAt": "2026-11-25T10:30:00Z",
  "modelVersion": "ppe-detector-v1",
  "idempotencyKey": "CAM_001-1764066600000",
  "workerId": null,
  "detections": [
    {
      "classLabel": "person",
      "confidence": 0.96,
      "bbox": [120, 80, 340, 520]
    },
    {
      "classLabel": "helmet",
      "confidence": 0.94,
      "bbox": [180, 80, 260, 150]
    },
    {
      "classLabel": "no_safety_vest",
      "confidence": 0.89,
      "bbox": [150, 160, 310, 380]
    }
  ],
  "missingPPE": ["safety_vest"],
  "safetyStatus": "UNSAFE",
  "overallConfidence": 0.89,
  "evidenceUrl": "evidence/2026-11-25/cam001_1764066600000.jpg",
  "evidenceFileHash": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
}
```

- **Example Response (`201 Created`):**
```json
{
  "success": true,
  "message": "PPE detection recorded",
  "data": {
    "detectionId": "det_01J9Z300",
    "cameraCode": "CAM_001",
    "zoneId": "zone_01",
    "safetyStatus": "UNSAFE",
    "incidentCreated": true,
    "cooldownMerged": false,
    "incidentId": "inc_01J9Z305"
  }
}
```

- **Validation & Error Responses:**
  - `400 Bad Request`: Invalid `safetyStatus`, confidence outside `[0.0, 1.0]`, malformed `detections` array, or unknown class label.
  - `401 Unauthorized`: Missing or invalid `X-ML-Service-Key`.
  - `404 Not Found`: Unregistered `cameraCode`.
  - `409 Conflict`: Duplicate `idempotencyKey` already processed.

### 8.2 Get Detection History & Details
- `GET /api/detections` — `SUPERVISOR` (assigned zones) or `ADMINISTRATOR` (all zones).
- `GET /api/detections/:id` — Returns single detection details.

## 9. Canonical Contract #3: Environmental Sensor APIs (`/api/sensors`)

### 9.1 Submit Sensor Event (`POST /api/sensors/events`)

- **Purpose:** Receives supplementary smoke or flame sensor readings from an ESP32 node, stores the event in `sensorEvents`, updates device `lastHeartbeat`, and generates or updates a `"SMOKE_DETECTED"` or `"FLAME_DETECTED"` incident when `alertStatus` is `"WARNING"` or `"CRITICAL"`.
- **Authentication Requirements:** ESP32 Device Authentication (`X-Device-Code` and `X-Device-Key` headers).
- **Required Headers:**
  ```http
  Content-Type: application/json
  X-Device-Code: ESP32_001
  X-Device-Key: <RAW_DEVICE_API_KEY>
  ```
- **Request Body Schema:**

| Field | Type | Required | Description & Validation Rules |
|---|---|---|---|
| `deviceCode` | String | **Required** | Registered ESP32 identifier (e.g., `"ESP32_001"`). Must match `X-Device-Code` header. |
| `sensorType` | String | **Required** | Canonical enum: `"SMOKE"` \| `"FLAME"`. |
| `sensorValue` | Number | **Required** | Numeric sensor reading (e.g., 12-bit ADC value `0..4095` or digital state `0` / `1`). |
| `threshold` | Number | **Required** | Configured trigger threshold used to evaluate the reading (e.g., `1500` or `1`). |
| `alertStatus` | String | **Required** | Canonical enum: `"NORMAL"` \| `"WARNING"` \| `"CRITICAL"`. |
| `occurredAt` | String (ISO 8601) | Optional | UTC timestamp of the reading; defaults to server reception time if omitted. |
| `firmwareVersion` | String | Optional | ESP32 firmware version string (e.g., `"1.0.0"`). |

- **Example Request:**
```json
{
  "deviceCode": "ESP32_001",
  "sensorType": "SMOKE",
  "sensorValue": 1850,
  "threshold": 1500,
  "alertStatus": "CRITICAL",
  "occurredAt": "2026-11-25T10:35:00Z",
  "firmwareVersion": "1.0.0"
}
```

- **Example Response (`201 Created`):**
```json
{
  "success": true,
  "message": "Sensor event recorded",
  "data": {
    "eventId": "sns_01J9Z400",
    "deviceCode": "ESP32_001",
    "zoneId": "zone_01",
    "sensorType": "SMOKE",
    "alertStatus": "CRITICAL",
    "incidentCreated": true,
    "cooldownMerged": false,
    "incidentId": "inc_01J9Z405"
  }
}
```

- **Validation & Error Responses:**
  - `400 Bad Request`: Invalid `sensorType`, non-numeric `sensorValue` or `threshold`, or invalid `alertStatus`.
  - `401 Unauthorized`: Missing or invalid `X-Device-Key`.
  - `403 Forbidden`: Unregistered or inactive `deviceCode`.

### 9.2 Get Sensor History & Latest Status
- `GET /api/sensors/events` — Returns paginated sensor history scoped by user role/zone.
- `GET /api/sensors/status` — Returns the latest smoke and flame status per registered ESP32 device in accessible zones.

## 12. Administrator APIs (`/api/admin`)

All `/api/admin/*` endpoints require `Bearer <JWT_TOKEN>` with `role: "ADMINISTRATOR"`.

- `GET /api/admin/overview` — System-wide counts across all zones, devices, cameras, workers, supervisors, and incidents.
- `GET /api/admin/supervisors` — List all supervisor accounts and their assigned zones.
- `POST /api/admin/supervisors` — Create a new supervisor account.
- `PUT /api/admin/supervisors/:id` — Update supervisor account.
- `DELETE /api/admin/supervisors/:id` — Deactivate supervisor account.
- `GET /api/admin/zones` — List all workplace zones.
- `POST /api/admin/zones` — Create a new workplace zone (`zoneCode`, `zoneName`, `description`).
- `PUT /api/admin/zones/:id` — Update workplace zone.
- `DELETE /api/admin/zones/:id` — Deactivate workplace zone.
- `POST /api/admin/zones/:id/assign-supervisor` — Assign a supervisor (`userId`) to a workplace zone (`zoneId`) in `zoneAssignments`.
- `DELETE /api/admin/zones/:id/assign-supervisor/:supervisorId` — Unassign a supervisor from a workplace zone.
- `GET /api/admin/audit-logs` — Retrieve paginated system audit logs (`actorId`, `actorRole`, `action`, `entityType`, `entityId`, `occurredAt`).

---

## 13. Dashboard and Analytics APIs (`/api/dashboard`)

All `/api/dashboard/*` results automatically filter by the authenticated user's role (`WORKER`: personal; `SUPERVISOR`: assigned zones; `ADMINISTRATOR`: system-wide).

- `GET /api/dashboard/overview` — High-level KPIs (`totalWorkers`, `activeWorkers`, `totalIncidents`, `openIncidents`, `verifiedIncidents`, `ppeCompliancePercent`, `activeDevices`, `activeCameras`).
- `GET /api/dashboard/analytics` — Time-series incident trends, violation breakdown by `incidentType` and `severity`, and PPE compliance percentage trends.
- `GET /api/dashboard/recent-activities` — Combined chronological stream of recent RFID scans, PPE detections, sensor events, and incident verifications.
- `GET /api/dashboard/zones` — Per-zone safety summary (assigned supervisor, active workers, online cameras/devices, open incidents, compliance percentage).

## 14. Real-Time WebSocket Events

Authenticated clients connect to the WebSocket server using their JWT and join role/zone-scoped rooms.

|---|---|---|
| `rfid:scan` | `{ logId, deviceCode, zoneId, recognized, scanStatus, worker, occurredAt }` | Zone Supervisors & Administrators (plus Worker if own scan) |

| `incident:new` | `{ incidentId, incidentType, severity, status, zoneId, description, createdAt }` | Zone Supervisors & Administrators |
| `incident:updated` | `{ incidentId, status, verifiedBy, resolvedBy, recordHash, updatedAt }` | Zone Supervisors & Administrators (plus linked Worker) |
| `device:status` | `{ deviceCode, zoneId, status, lastHeartbeat }` | Zone Supervisors & Administrators |
| `camera:status` | `{ cameraCode, zoneId, status, lastHeartbeat }` | Zone Supervisors & Administrators |

## 15. Future Scope: Blockchain Verification APIs (`/api/blockchain`)

These endpoints are reserved for the **future on-chain blockchain anchoring extension** (`NOT STARTED`). For initial prototype tamper-evidence, use `GET /api/incidents/:id/verify-integrity` (Section 10.4).

- `POST /api/blockchain/record` — Anchors an already-computed incident `recordHash` (SHA-256) onto a configured smart contract and saves `blockchainTxHash`.
- `GET /api/blockchain/verify/:incidentId` — Compares the database `recordHash` against the on-chain smart contract record.

## 16. Standard HTTP Status Codes

| Status Code | Meaning |
|---|---|
| `200 OK` | Request succeeded |
| `201 Created` | New resource or event record created |
| `400 Bad Request` | Payload validation failed (missing required field, invalid enum, or out-of-range value) |
| `401 Unauthorized` | Missing, invalid, or expired JWT or device/ML service API key |
| `403 Forbidden` | Authenticated caller lacks role permission or zone scope for the requested resource |
| `404 Not Found` | Requested entity ID, `deviceCode`, or `cameraCode` does not exist |
| `409 Conflict` | Duplicate unique field (`email`, `employeeCode`, `rfidUid`, `deviceCode`, `cameraCode`, `idempotencyKey`) |
| `429 Too Many Requests` | Rate limit exceeded |
| `500 Internal Server Error` | Unhandled server error (sanitized error response returned) |
